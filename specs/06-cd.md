# 06 — CD pipeline

Implements flow Ⓒ–Ⓓ, O3, O6, O8 and Pushback #4, #5, #10–#12 from `architecture.md`.
GitHub Actions does **CD only**; CI (the full suite on a GPU) is the GPU host's job.

## Purpose

On a schedule or on demand, take `master`, build everything, publish a Release and Pages,
and deploy to the VPS — restarting the realm only when it is safe to.

## Scope

In: the workflow, build steps, artifact layout, manifest generation, the ssh deploy
script, gating, tagging, rollback invocation. Out: running the GPU suite; building for
platforms other than Linux/Windows x86_64; anything the agent does on the GPU host.

## Repository assumptions

After spec 09, `N3E-Realm` contains the engine, client, tooling, tests and content
source. The only external input CD fetches is the raw KO asset tarball, pinned by
sha256 in `UPSTREAM.md` and stored as a Release asset of this repo, via
`tools/fetch-ko-assets.sh` into the ignored `assets/ko/` (spec 10). The realm package is
`games/moradon` cooked by `tools/assetc`.

## Interfaces

### Workflow `.github/workflows/cd.yml`

```yaml
on:
  schedule: [{ cron: "17 * * * *" }]           # hourly; cheap when nothing changed
  workflow_dispatch:
    inputs:
      force:  { type: boolean, default: false } # restart even with players online
      reason: { type: string,  default: "" }
      ref:    { type: string,  default: "master" } # a deploy-* tag for rollback (O6)
concurrency: { group: cd, cancel-in-progress: false }
```

Jobs, in order (each a separate job so failures are legible):

1. **`changed`** — compute what differs from the last `deploy-*` tag, by path:
   `server` (`server/`, `protocol/`, `deploy/*.sql`, `Cargo.*`), `bot` (`bot/`),
   `client` (`client/`, `protocol/`, `CMakeLists.txt`), `content` (`games/moradon/`,
   `tools/assetc/`, the KO pin in `UPSTREAM.md`), `docs`, `launcher`. If nothing differs
   and not forced: stop here, green, "no changes".
2. **`test`** — headless gate (Pushback #11): `make server`, `cargo test`, and the
   non-graphical subset of `make test` listed in `ci/headless-tests.txt` (the full
   `make test` builds the client and runs GL checks; the hosted runner has no GPU and
   `make live` is the GPU host's job). Plus `cargo test` for `bot/` and `launcher/`.
3. **`build`** (matrix) —
   - `server`: `docker build -f deploy/Dockerfile --build-arg N3E_BUILD_VERSION=…` → `ghcr.io/<org>/n3e-server:<sha>`.
   - `bot`: `bot/Dockerfile` → `ghcr.io/<org>/realm-bot:<sha>`.
   - `client-linux-x86_64`: build in a **builder image** `ghcr.io/<org>/n3e-client-builder:<toolchain-hash>` (Ubuntu 24.04 + SDL3 ≥ 3.2 built from source + protobuf + OpenSSL dev). The builder image is rebuilt only when `ci/client-builder/Dockerfile` changes (Pushback #12). Output: `n3e-client-linux-x86_64.tar.zst` containing the binary plus any required shared objects that are not in a stock distro (SDL3).
   - `client-windows-x86_64`: `windows-latest`, vcpkg manifest (`vcpkg.json`: `sdl3`, `protobuf`, `openssl`, `opengl-registry`; triplet `x64-windows-static`), CMake; output `n3e-client-windows-x86_64.tar.zst` holding one static `n3e-client.exe` (the Launcher reads one archive format on both platforms).
   - Both client archives are written by `tools/package_client.py`; the Linux one carries `libSDL3`, protobuf and abseil beside the binary (RUNPATH `$ORIGIN`).
   - `launcher-linux-x86_64`: `cargo build --release --target x86_64-unknown-linux-musl`.
   - `launcher-windows-x86_64`: `cargo build --release --target x86_64-pc-windows-msvc`.
   - `content`: `tools/fetch-ko-assets.sh` (Actions cache keyed by tarball sha256) then `python tools/assetc/main.py games/moradon out/content`; `hash=$(cat out/content/release.sha256)`; write `content-<hash>.index.json` (per-file sha256/size, spec 04); upload each file not already present in the content-addressed store. Also a `realm-content:<hash>` image for the server (below). If `package.json.progression` changed since the last deploy tag, set `PROGRESSION_CHANGED=true`.
3b. **`smoke`** (matrix `ubuntu-latest`, `windows-latest`) — download that platform's
   launcher + client artifacts; run `realm-launcher --manifest <local file> --no-start`
   to assemble a package from the just-built content index (served from the job's
   workspace via a local HTTP server); then `n3e-client <package> --self-test --realm
   realm.json` must exit 0 within 60 s. No server, no network beyond localhost.
   Mesa llvmpipe on both runners (`SDL_VIDEO_DRIVER=offscreen` on Linux; Mesa's
   `opengl32.dll` beside the client on Windows). `tests/release_smoke.py` is this step;
   CI's `client` job (M4b) already runs it on the demo package for every push.
   **Failure blocks publish.** (`--self-test`, not the `--smoke-local` first planned:
   the player build may carry no `smoke` string, PQ-006 / `tests/player_build.py`.)
3c. **`sign`** — no-op until a signer is configured (Q26). Placeholder step so enabling
   SignPath/OV signing is configuration, not a workflow change.
4. **`publish`** — write `manifest.json` (spec 04) from the build outputs; create Release
   `v<YYYY.MM.DD>-<shortsha>` with binaries, `manifest.json`, the content index, and the
   store files; **publish before deploy** (Pushback #5). Build Pages (spec 08) and deploy
   them.

   **Content-addressed store.** GitHub Release assets must be unique per Release, so the
   store is a *rolling* Release named `content-store` whose assets are `<sha256>` files;
   `base_url` in every manifest points at it. CD uploads only missing files and prunes
   files no manifest from the last 20 Releases references. (If the store outgrows
   Release-asset limits — 2 GiB/file is fine, count is the risk — move it to an object
   store; `base_url` makes that a one-line manifest change. Q25.)
5. **`deploy`** — ssh to the VPS and run `deploy/remote.sh` (below). Skipped entirely if
   `changed` says only `docs`/`launcher` changed.
6. **`tag`** — on successful deploy, tag `deploy-YYYYMMDD-HHMM` at the deployed commit
   and push the tag.

### `deploy/remote.sh` (runs on the VPS, as the deploy user with sudo for compose)

Inputs via env from the ssh command: `IMAGE_TAG`, `CONTENT_HASH`, `FORCE`, `REASON`,
`RESTART_SERVER` (true if `server` or `content` changed), `RESTART_BOT`, `HEAD_SHA`,
`COMMITS_BEHIND`, `PROGRESSION_CHANGED`.

```
set -euo pipefail
cd /opt/n3e-realm
OPS=$(sudo cat /etc/n3e-realm/ops.token)
api() { curl -fsS -m 5 -H "Authorization: Bearer $OPS" "$@" http://127.0.0.1:7780/v1/"$1"; }

docker compose pull                                 # all images, idempotent
[ "$RESTART_BOT" = true ] && docker compose up -d bot              # never kicks anyone

if [ "$RESTART_SERVER" != true ]; then api realm/deploy-pending -X DELETE; exit 0; fi

status=$(api realm/status) || { echo "admin API down; refusing to deploy"; exit 3; }
players=$(jq .players <<<"$status")
if [ "$players" -gt 0 ] && [ "$FORCE" != true ]; then
  api realm/deploy-pending -X PUT -d "{\"since\":\"$(date -u +%FT%TZ)\",\"commits_behind\":$COMMITS_BEHIND,\"head\":\"$HEAD_SHA\"}"
  echo "skip: $players online"; exit 0
fi

if [ "$FORCE" = true ] && [ "$players" -gt 0 ]; then
  # KO's /serverdown cadence: one in-game NOTICE line per minute (KO-FINDINGS.md §1)
  for m in $(seq "${COUNTDOWN_MIN:-2}" -1 1); do
    api realm/notice -d "{\"text\":\"The server will restart in $m minute(s): $REASON\",\"level\":\"warn\",\"in_game\":true}"
    sleep 60
  done
fi
api realm/drain -d "{\"reason\":\"$REASON\"}"
for i in $(seq 60); do [ "$(api realm/status | jq .players)" = 0 ] && break; sleep 2; done   # ≤ 2 min
# O3: dump → migrate → restart, in that order
sudo -u postgres pg_dump n3e | zstd > /var/backups/n3e-realm/pre-deploy-$(date -u +%Y%m%d-%H%M).sql.zst
docker compose run --rm migrate
if [ "$PROGRESSION_CHANGED" = true ]; then
  # content/reward-upgrades.md: durable reward-policy change needs the upgrade path, run against the *old* package
  docker compose run --rm server upgrade-progression /package-previous || { api realm/resume; exit 5; }
fi
docker compose up -d --force-recreate content-init server
docker compose exec -T server n3e-server health || { echo "server not ready"; exit 4; }   # retries inside
api realm/deploy-pending -X DELETE || true           # drain state is memory-only; gone with the restart
```

Content is delivered to the server as part of the server image or as a volume:
**decision** — bake the cooked package into a tiny `ghcr.io/<org>/realm-content:<hash>`
image and mount it via a compose `volumes_from`-style init container that copies it
to a named volume before `server` starts. This keeps "what is deployed" fully
described by image digests. (Alternative: rsync the package over ssh. Rejected: two
delivery paths.)

### Versioning

- Release name / client version / `status.version`: `v<YYYY.MM.DD>-<shortsha>`.
- Images tagged with the full SHA and `latest`; compose uses the SHA (written into
  `/opt/n3e-realm/.env` as `IMAGE_TAG` by `remote.sh`).
- Deploy tags `deploy-YYYYMMDD-HHMM` are the rollback handles.

### Rollback (O6)

`workflow_dispatch` with `ref: deploy-YYYYMMDD-HHMM` and `force: true`. The pipeline
rebuilds nothing if the images for that SHA still exist in GHCR (they do; keep 20) and
re-runs `publish` (re-pointing `latest` Release — GitHub needs the Release to be
re-marked latest) and `deploy`. DB rollback is manual from the pre-deploy dump (O3/O4).

## Behaviour notes

- **Order matters:** Release published → Pages → deploy. A client that updates before
  the realm restarts is fine (handshake `CONTENT` mismatch until restart means "wait
  a minute", and n3e's error names it). A realm that restarts before the Release exists
  strands every player — spec 04 exit 20 detects it; CD must make it impossible.
- The hourly cron is a no-op when `changed` is empty. Expect ~1 min of runner time.
- CD never holds the ops token; it reads it on the VPS over ssh.
- Secrets in GitHub: `VPS_SSH_KEY`, `VPS_HOST`, `VPS_USER`. Nothing else (O5).
- `GITHUB_TOKEN` default permissions: `contents: write` (Releases, tags), `packages:
  write` (GHCR), `pages: write`, `id-token: write` (Pages).

## Failure modes

| Stage | On failure |
|---|---|
| `test` | Stop. Nothing published. Open an issue automatically? No — the agent loop reads Actions status itself (spec 08 lists where). |
| `build` | Stop. |
| `publish` partial (Release created, assets missing) | Delete the draft Release and fail; a Release is created as a draft and published atomically at the end of the job. |
| `deploy`: admin API down (exit 3) | Fail the job; the realm is probably mid-restart from something else. The next cron retries. |
| `deploy`: players never reach 0 within 2 min after drain | Proceed with the restart anyway (drain already told them). Log it. |
| `deploy`: migration fails | `migrate` container exits non-zero → script exits before `up -d` → old server keeps running (it was never stopped). The pre-deploy dump exists. Fail the job loudly; Bot sees `realm.draining` with no `realm.ready` — add a `realm.resumed` call in a trap so the realm reopens. |
| `deploy`: `upgrade-progression` fails (exit 5) | Old server untouched, drain lifted, dump present. A balance PR that cannot upgrade needs a human. |
| `deploy`: server not healthy after restart | Exit 4. Do **not** auto-rollback (it would restart again); page a human via the ops channel: `remote.sh` posts a `notice` with `level: warn` in its `trap`. |

## Acceptance tests

1. **No-op cron.** With `master` == last `deploy-*` tag, the run finishes green in
   `changed` only.
2. **Bot-only change.** Only `bot/` differs → images built, Release published, bot
   restarted, server untouched (uptime unchanged), no drain event.
3. **Server change, nobody online.** → dump exists, migrate ran, server restarted,
   `deploy-*` tag pushed, `deploy_pending` null, `realm.ready` on the stream.
4. **Server change, player online.** → no restart; `deploy_pending` set with the right
   `head`; Bot posts the pending message once; second cron with same head posts
   nothing new.
5. **Force.** `workflow_dispatch force=true` with a player online → two in-game
   NOTICE lines one minute apart (test client asserts receipt), drain, restart.
6. **Ordering.** Release assets are downloadable **before** the ssh step starts (assert
   in the workflow by curling the manifest URL in `deploy` before ssh).
7. **Rollback.** Dispatch with a previous `deploy-*` tag → the realm reports that
   version; the Launcher's `latest` manifest points to it.
8. **Migration failure.** Inject a failing migration → job fails, old server still
   serving, drain lifted (`realm.resumed` seen), dump present.
9. **Secrets.** `grep -r` the workflow for `ops.token`, Discord tokens: zero hits.
