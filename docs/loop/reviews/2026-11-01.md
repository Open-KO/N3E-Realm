**Overall.** The code is in better shape than the docs.
- These parts hold up:
  - Admission order and counters.
  - Token hashing and logging.
  - The admin API's permission table, bounds and bind check.
  - realm-edge's framing, bounds and PROXY v2 bytes.
  - The launcher's path safety and atomic install.
  - The bot's consumer-group handling.
  - The N3FE writer and reader byte layout.
  - Engine hygiene: no game IDs in engine modules, no blocking I/O on the tick, no unbounded channels.
- The serious problems are a handful of security and correctness edges, listed in §1–§2.
- The VPS-era ops specs (06, 07) no longer describe the host they would deploy to (§3.1).
- Several acceptance tests assert less than their spec says (§4).
- The loop's own gate has blind spots (§6). Those are for the maintainer: the loop does
  not file items about its own machinery.

Severity order inside each section: the first item matters most.

## 1. Security

1. **Trusted-proxy CIDR, server: a bare IPv4-mapped address trusts every IPv4 peer in a release build** (extends RQ-036).
   - `server/src/admission.rs:80-91` keeps a prefix of up to 128 for an address that `canonical()` (`:94-98`) then turns into IPv4.
   - `within()` computes `32 - bits as u32` (`:104`). In release builds this wraps, because the Cargo profiles set no `overflow-checks`.
   - `checked_shl` then returns `None`, so the mask is `0` and every IPv4 address matches.
   - `N3E_TRUSTED_PROXY_CIDRS=::ffff:172.31.77.11` (no prefix, so 128) is enough to trigger it, as well as RQ-036's `/104`.
   - Effect: any client may send a PROXY v2 header naming any source, which bypasses spec 01's per-source limits.
   - Production uses `172.31.77.11/32` (`deploy/HOST.md:66`), so it is not exposed today.
2. **Trusted CIDRs, edge: a mapped range shorter than /96 trusts every IPv4 peer.**
   - `edge/src/config.rs:106` uses `bits.saturating_sub(96)`, so `::ffff:a.b.c.d/80` becomes IPv4 `/0`.
   - RQ-036's text says the edge already refuses such ranges ("refuse one under 96, as realm-edge does"). It does not.
3. **Pre-auth slots are held without a time limit after the Handshake.**
   - The idle deadline ends at the first frame (`server/src/network.rs:266-289`). After that, each read has a 2 s deadline (`:508-510`), and any frame resets it, a `Ping` included (`:816`).
   - The slot is released only when login completes or the socket drops (`server/src/admission.rs:317-327`).
   - With the defaults (16 slots, 3 per source), 6 sources that send a Ping every second, or 6 IPv6 /64s, hold every pre-auth slot for as long as they like.
   - Every other connection is then reset at accept, with no reason given.
   - Spec 01 (lines 15-17, 89) allows this. The spec needs amending along with the code.
4. **The launcher follows redirects, including from https to plain http.**
   - `launcher/src/net.rs:35-59` checks Q43's rule on the first URL only.
   - `Net::new` (`:107-124`) sets neither `https_only` nor a redirect limit. The ureq 3 defaults are `https_only: false` and `max_redirects: 10`.
   - The manifest names the client's sha256, so it is the trust root.
   - Q66 explicitly allows a redirect for the default realm's URL.
5. **Artifact `sha256` strings are used in file names without a hex check.**
   - `launcher/src/install.rs:88` builds `client-{sha256}`, and `launcher/src/run.rs:173-175` builds `launcher-{sha256}`.
   - `check_manifest` (`run.rs:108-126`) checks the hex form only for `content.hash` and `index_sha256`.
   - A `../` value writes a `.part` file outside `downloads/`.
6. **The login throttle is keyed on the full address, not spec 01's /64 bucket.**
   - `server/src/network.rs:287` passes `source.to_string()`, and `server/src/cache.rs:168-170` uses it as the key.
   - Admission buckets by /64 (`admission.rs:115-120`).
   - So one IPv6 /64 can multiply the 30/IP/min login limit and the number of Discord code exchanges.
7. **The production compose file publishes the game port on every interface by default.**
   - `deploy/compose.prod.yaml:70` has `${N3E_BIND:-0.0.0.0}`. On the home host, only `.env` keeps `:7777` off the LAN, and Docker bypasses the host firewall.
8. **CI's no-KO-native-files check covers `games/**` and six extensions only.**
   - The check is at `.github/workflows/ci.yml:34`. `docs/architecture.md` ("Raw KO assets") says a PR adding a KO-native file fails CI anywhere in the repo.
   - The pinned tree also has `fxb`, `gtt`, `wav`, `mp3`, `tga`, `bmp`, `.tbl.csv`, `brd` and others.
   - `git ls-files` tracks no such file anywhere today, so this is a gap in the check, not a leak.
9. **The bot accepts any https `GITHUB_API`, and that host would receive the PAT** (`bot/src/config.rs:257-265`).
   - Q39 says the stand-ins are refused unless they are on loopback.
   - Spec 05:36 allows https. One of the two texts is wrong.
10. **Refused admin calls are not logged.**
    - The 401, 403 and bad-body paths (`server/src/admin_api.rs:814-837`) return before the `admin by=… result=…` line (`:840-845`).
    - Spec 03:244 asks for `result=<code>` on every mutation.

## 2. Correctness

1. **A ban or kick can commit and still leave the player online.**
   - `server/src/admin_api.rs:1127-1131` wraps `sessions::change` in a 2 s timeout and answers 503 on timeout.
   - `Database::call` cannot be cancelled: its own comment, `server/src/accounts.rs:104-106`, warns against exactly this timeout. So the change still commits.
   - `live.kick` and `live.mute` and the stream event (`admin_api.rs:1132-1158`) are skipped.
   - There is also a smaller race: a login that committed just before the ban registers in `Live` only afterwards (`network.rs:533-539`).
2. **One `accept()` error ends the realm.**
   - `server/src/network.rs:927` and `server/src/admin_api.rs:648` both use `listener.accept().await?`.
   - The `select!` at `server/src/main.rs:845` then ends and the process shuts down.
   - accept(2) can fail transiently: ECONNABORTED, EMFILE, ENOBUFS and others.
3. **`/deploy force:True` cannot run while the admin API is down.**
   - `bot/src/commands.rs:597-604` calls `realm/status` and returns on trouble before it looks at `force`.
   - That is the moment a forced deploy is needed. Spec 05:63 needs the status only when `force` is not passed.
4. **A message Discord permanently refuses stalls the event stream for good.**
   - A failed post is never acknowledged and is retried forever (`bot/src/stream.rs:170-185, 198-204`).
   - A deleted channel, or a lost permission, silently stops every later announcement.
   - Spec 05:76-79 mandates the retry, so the spec needs amending too.
5. **Bot duration parsing panics on a multi-byte last character.**
   - `bot/src/text.rs:50` calls `split_at(t.len() - 1)`, which panics on input such as `/ban … 1ö`.
   - `n * seconds` at `:65` is not overflow-checked.
6. **The client's OAuth callback poll can freeze a frame for 2 s.**
   - `client/network/discord_login.cpp:432-444` accepts a connection and then loops on `net::wait(…, 100)` for up to 2 s.
   - Spec 02:168 says the poll never blocks a frame. Browsers open idle preconnect sockets, which triggers this.
7. **After a transient `SessionLogin` refusal, ENTER sends the player through Discord again.**
   - A refusal such as `dependency` or `login rate limit` moves the flow to `idle`, and ENTER in `idle` starts the browser flow (`discord_login.cpp:549-572`).
8. **The client never embeds `N3E_BUILD_VERSION`** (spec 09, tweak 5; M0 is marked done).
   - `client/` and `CMakeLists.txt` have no `BUILD_VERSION`.
   - The loading screen's `{version}` is the package's `release.version` (`client/render/viewer.cpp:2937`).
   - Spec 11 says it is the client version. Spec 03's `status.version` and spec 06's manifest cannot agree with it.
9. **Launcher edge cases:**
   - A zero-byte content file fails every install with exit 11 (`launcher/src/net.rs:195-202`: no `.part` is created, so the hash fails).
   - After a client exit 3, any failure to read the manifest becomes exit 20, "CD ordering bug" (`launcher/src/run.rs:584-610`). A schema refusal should give 12.
   - An oversize manifest or index is reported as a network error rather than a verification failure (`net.rs:148-153`).
   - The index `schema` is never checked (`install.rs:174-210`).
10. **The launcher's "manual download" URL is the manifest itself for any realm not on GitHub, the default included.**
    - `releases_url` (`launcher/src/run.rs:101-106`) rewrites only URLs containing `/releases/`.
    - `https://releases.openko.net/manifest.json` does not contain it.
    - Every min_version, exit-10 and schema refusal on OpenKO therefore points players at a JSON file.
11. **The front-end cook can produce a blob every client refuses.** With the silent fallback, a bad package reaches players as the plain panels.
    - `tools/assetc/ko_front_end.py:364-373` records an action as bound and then returns without writing the node when the image is untextured.
    - The cook does not check that the slot count equals `character_slots` (`:508, :559`), or the loader's ASCII, rect and flag bounds.
    - Spec 11 ("Security") says every bound is checked in both the cook and the loader.
12. **The front-end fonts are absolute host paths, rasterised by the host's ImageMagick.**
    - `games/moradon/front-end.json:4-5` uses `/usr/share/fonts/liberation/…`, and so does `games/moradon/nameplates.json:9` and `tools/assetc/ko_hud.py:311`. That path is Arch's layout; Ubuntu uses `/usr/share/fonts/truetype/liberation/`.
    - `ko_nameplates.atlas` shells out to `magick`.
    - Nothing pins or hashes the fonts or the rasteriser.
    - So spec 11 test 5 ("deterministic") holds only per host, and CD's Ubuntu cook (RQ-030) will fail or produce another hash. RQ-014 picks the face; it does not pin it.
13. **A legacy `Login` naming a Discord-created account panics** (only with `N3E_LEGACY_LOGIN=1`).
    - Since migration 025 the account's `salt` is NULL, and `server/src/accounts.rs:265-279` reads it as `Vec<u8>`.
    - Also, `account-create d<snowflake>` breaks that Discord user's upsert (`sessions.rs:164-166`).
14. **Admin notices are truncated to 256 characters, not 256 bytes.**
    - `server/src/admin_api.rs:216-217, 949` truncates by characters, against the chat bound of 256 bytes (`simulation.rs:1896`).
15. **The launcher keys an installed client by its version string only** (`install.rs:71-73`).
    - Two realms, or a republish, with the same `client.version` and a different archive share one install that was never verified against the second manifest.
    - Spec 04:235 says every artifact is verified before exec.

## 3. Contract drift (specs against code)

### 3.1 The ops specs and the home host (Q64, spec 12)

Q64 and M7a moved the realm to the realm host behind a Cloudflare Tunnel. Specs 06 and 07
still describe an ssh-reachable x86_64 VPS:

- **CD reaching the host.** Spec 06's `deploy` ssh-es in (`06-cd.md:83, 90, 161`). The host has no inbound port. This is Q67, raised here.
- **Image architecture.** CD builds x86_64 images on hosted runners (`06-cd.md:14-15, 51-59`), but the host is aarch64 (`deploy/HOST.md:8`).
- **Image names and paths.**
  - Spec 06:53 builds `bot/Dockerfile`, which does not exist. The real build is `deploy/Dockerfile --target bot`.
  - There is no edge image in the build, no `edge/` in `changed`, and no `RESTART_EDGE`.
  - Spec 06's `ghcr.io/<org>/n3e-server:<sha>` and `IMAGE_TAG` do not match compose's `N3E_IMAGE`, `N3E_BOT_IMAGE` and `N3E_EDGE_IMAGE` (`deploy/compose.prod.yaml`).
  - `remote.sh` runs bare `docker compose`, without `-f deploy/compose.prod.yaml` or the `edge` profile.
  - `content-init` (`06-cd.md:128`, `07-deploy.md:96-98`) is not in `compose.prod.yaml`.
- **The pre-deploy dump.** `sudo -u postgres pg_dump n3e` (`06-cd.md:122`) cannot work on any host: Postgres runs only in a container. It should be `docker compose exec -T postgres pg_dump …`.
- **The releases route.**
  - Spec 12:118-120 and the comment at `deploy/compose.prod.yaml:132-133` say `releases.openko.net` "goes away" once CD publishes GitHub Releases.
  - Q66 and `launcher/src/profiles.rs:17` make `https://releases.openko.net/manifest.json` permanent: players' `realms.json` stores it.
  - Following spec 12 would strand every installed launcher.
  - Until M5, the downloads come from the home uplink through the tunnel. `docs/architecture.md`'s DDoS table assumes GitHub absorbs them.
- **Q63 and realm resets.**
  - Q63 says a progression change starts a new realm.
  - The realm name includes the package hash (`deploy/HOST.md:13`), so *any* content change starts a new realm and characters do not carry over.
  - Spec 06's hourly cron would reset characters without warning.
- **Spec 07 against the host:**
  - TLS paths: spec 07 has `fullchain.pem`/`privkey.pem`; compose mounts `server.pem`/`server.key`.
  - The renewal hook calls `remote.sh --local`, which does not exist. The host renews daily from a crontab with `tools/host-tls`.
  - The `.env` list (07:56-70) lacks `CLOUDFLARE_TUNNEL_TOKEN`, `N3E_BIND`, `N3E_TRUSTED_PROXY_CIDRS`, `N3E_TLS_PATH` and `N3E_PACKAGE_PATH`.
  - R2 has no rows for the tunnel or DNS tokens, although spec 12:141 says R2 applies to them.
  - The firewall rules and acceptance test 2 ("nmap shows 22 and 7777") contradict spec 12, under which nothing listens publicly.
  - Backups: spec 07 has an object store; `HOST.md:35` has none yet. This is Q68, raised here.
  - **Not verified:** the review did not read `tools/host-tls`, which is out of bounds. Whether a renewal restart waits for an empty realm is for the maintainer to confirm.
- `docs/architecture.md` (the Delivery diagram, O1/O4/O5, Deploy gating, Pushback #13) and Q15 (an uptime check on 7777/7781, which are not public now) also still describe the VPS.

### 3.2 Specs 01–03 and the architecture

- **Admin audit for token calls (spec 03 test 6) is not implemented.**
  - Spec 03:209-217 and test 6 (03:271-272) ask for an `admin_audit` row with `token_name`. The roadmap's M1 (`00-roadmap.md:27`) lists it as delivered.
  - No server code writes `token_name` (grep: only `deploy/024-admin-tokens.sql:12-18`).
  - The schema cannot hold such a row as it stands:
    - `reason` is checked at ≤ 160 characters (`deploy/006-administration.sql:24`), but account reasons go up to 200.
    - `revision`, `before_state` and `after_state` are NOT NULL.
    - `admin_results` is keyed on `character_id`.
  - `docs/architecture.md` ("Admin tokens", "Not doing") says there is no audit beyond `last_used_at`.
  - Kicks, bans and mutes done through the bot are recorded only in Redis and on stderr. That breaks AGENTS.md: "Redis is never the only copy".
- **Event payloads.** `realm.draining` and `realm.resumed` carry `by` (`admin_api.rs:906, 913`, and the test pins it), but spec 03:228-229 omits it.
- **Error bodies.**
  - Transport errors use prose and an extra `limit` field (`admin_api.rs:679, 707, 716, 739`).
  - A bad Content-Length closes the connection without answering 400.
  - The codes the bot actually sees (`bad_request`, `not_found`, `method_not_allowed`, `unavailable`) are not listed in spec 03.
- **Spec 03 test 6** says a muted client gets "one notice line". The code and spec 02:135 send `Error{FORBIDDEN,"muted:…"}`, so spec 03 is the stale side.
- **Spec 01 against the code:**
  - The `N3E_LISTEN` default is `0.0.0.0:7777` in spec 01:32 and `127.0.0.1:7777` in the code (`main.rs:840`). The code's default is the safer one, so the spec should change.
  - Pre-auth timeouts and TLS failures close normally, not with the reset spec 01:74-77 specifies (only `refuse()` sets linger 0, `network.rs:896-898`).
- **Spec 02 test 5** says the old token gets `banned:…`. A ban deletes every session (spec 02:139), so the old token gets `revoked`, which is what the test asserts (`tests/discord_login_live.py:331`).
- **Architecture, Sessions.**
  - It says logout deletes the session row. The code keeps the session (`network.rs:828`), and a test relies on that (`discord_login_live.py:228-237`).
  - It says "Revocation is immediate" and uses `revoke NAME`. Spec 03 has `revoke --name` and a 10 s cache.
- **The bot's 401 alert re-arms on any outcome that is not a 401** (`bot/src/commands.rs:265-268`). Spec 05:129 says it re-arms only after a call succeeds.
- **Bot start-up checks.** `REALM_REDIS` and `GITHUB_WORKFLOW` are not validated at start (`bot/src/config.rs:248-253, 273`), against spec 05:39.
