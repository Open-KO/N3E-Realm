# Contribution settlement and progression (KO-09)

Optional `progression.bin` is release-hashed **N3P1**, engine **9**, protocol **4**.
Older releases keep their existing readers, protocol and atomic legacy item+XP
behavior. The new mode is inactive for ordinary startup until KO-10. The
approved semantics remain authoritative.

## Package definition

The manifest's `progression` object supplies `model=contribution_claim_v1`,
`stat_policy=fixed_v1`, namespaced `curve` and `item`, `origin=original synthetic`,
`author`, positive `revision`, ten cumulative `thresholds`, `capacity`, `starting`,
`npc_level`, `base_xp`, `radius`, `claim_radius` and `ttl`. Inventory fields must
match gameplay. Bounds: ten strictly increasing signed-bigint thresholds beginning
at zero; capacity 1..64; starting 0..capacity; NPC level 1..10; XP 1..1,000,000;
eligibility radius 1..100m; claim radius .5..10m; TTL 10..600 seconds.

Encoding is little endian, with no padding:

| Order | Encoding |
|---|---|
| Header | four bytes `N3P1`; u32 policy=1; u32 fixed-stat policy=1 |
| Identity/provenance | curve, item, origin, author: each u32 byte length + UTF-8 bytes |
| Table | u32 revision; ten u64 thresholds |
| Reward | u32 capacity, starting, NPC level, base XP; f32 radius, claim radius; u32 TTL |

No trailing bytes. SHA-256 of the entire N3P1 file is the independently persisted
reward-definition identity. Cosmetic assets may change without changing it.
Recipe, N3P1 dependency and release hashes retain the original table's provenance.
Producer and both readers validate bounds, inventory agreement and compatibility.
The original lab is generated by `python tools/assetc/progression_fixture.py`;
KO-11 now selects this policy with engine10/wire5 in `games/demo`; older packages remain unchanged. Fixed stats mean no level-up heal, resource refill,
attribute/skill points or ability recalculation.

## Frozen settlement identity

N3S2 is an internal canonical **settlement payload**, not a client request or asset.
All integers are little endian; positive IDs fit signed bigint. Scope is the
separate `(realm,encounter)` database key. Layout:

1. Four bytes `N3S2`.
2. u64 encounter, source realm generation, death tick, reserved claim operation.
3. 32 raw release-hash bytes, then 32 raw definition-hash bytes.
4. u32 zone byte length followed by UTF-8 bytes (1..128).
5. Three exact finite f32 death-position components, each within ±1,000,000.
6. u8 owner-present (0/1), followed by i64 owner (zero when absent).
7. u32 contributor count (0..64); ascending unique character IDs.
8. Each contributor: i64 character; u64 capped credit; u32 reason; u32 frozen level;
   u64 awarded XP. Reason 0=eligible, 1=disconnected, 2=dead, 3=other zone,
   4=outside radius. Disconnected rows use level 1 as a non-awarding placeholder;
   connected rows use their current level. No session token enters the payload.

The largest legal payload is 2,305 bytes, below the 32KiB contract ceiling.
Full bytes and SHA-256 must match on a retry. The independent hex fixture is
[golden-settlement-payload.hex](../protocol/golden-settlement-payload.hex).
Both wire implementations also generate the independent
[settlement result vector](../protocol/golden-settlement.hex).
The current one-zone realm uses its game namespace as the stable death-zone key.

Ledger credit is capped by pre-hit HP. Home healing waits for a reserved fresh
instance ID, then abandons all credit. Eligibility freezes at the lethal command;
subsequent session/death changes cannot revoke it. Capacity admission runs after
ordinary action validation and before cost/damage. For conservative reservation,
a saturated settlement queue or empty ID pool rejects **all otherwise-valid
attacks**, including nonlethal hits/misses, until capacity returns. Existing
contributors may continue when only the 64-entry ledger is full. No ledger eviction.

At most 64 settlement jobs are retained, with at most eight completed settlement
results applied per tick (each has at most 64 recipient records). A settlement
updates all its connected recipients together, and only newer progression revisions.
Join reloads progress to cover a commit between network selection and tick admission.
Neither settlement completion nor reload installs an old entity/life/session.

## Wire 4

Inventory adds `curve_xp` (9), `revision` (10), `latest_settlement` (11) and
`settlement_status` (12). Lifetime XP and server-calculated level retain their
fields. Legacy `last_operation`, `pending` and `reward_status` keep their old
operation-family meaning. No pending XP or inventory is published as committed.

Envelope 21 is read-only `SettlementStatus { encounter=1 }`. Envelope 22 is
`SettlementResult { encounter=1, status=2, awarded_xp=3, xp=4, curve_xp=5,
level=6, revision=7, reason=8 }`. Only an authenticated current recipient can read
its own immutable result. Other/unknown IDs return `unknown`. Status describes
the settlement (`entitled`, `loot_capacity`, `no_recipient`), not a promise that
the querying recipient owns the item. Claim ownership/discovery and UI are KO-10.
Historical results do not overwrite current progression. No client message can
submit a settlement, eligibility list, award, definition or claim ID.

## Database and conversion

Migration 005 installs empty new tables, restrictive history foreign keys,
immutable-result/entitlement-identity triggers and recovery indexes. Absence of a
realm policy row means legacy. Migrations 001–004 and `reward_operations` are
unchanged. All new characters in a converted realm initialize both progression
counters and inventory in the character creation transaction.

`N3E_TEST_PROGRESSION=disposable`, a `test-` realm name and the opt-in package are
all required for conversion/startup. With admission stopped and jobs drained:

```sh
N3E_PACKAGE=build/packages/progression-lab \
N3E_REALM=test-progression N3E_TEST_PROGRESSION=disposable \
  target/debug/n3e-server convert-progression
```

`DATABASE_URL` must point to an isolated, migrated test database. Conversion uses
the package's retained gameplay `level_xp` as the explicitly selected legacy
divisor; the operator must match the old realm's divisor, item and capacity.
It acquires an exclusive realm lease, locks characters in ascending order,
preserves inventory/lifetime XP/life/roles/old results, and records X/q/remainder,
divisor and definition. Level above 10 aborts all conversion with the affected ID.
Repeating the same conversion is read-only; changing definitions or loading a
legacy package after conversion fails. No live conversion is part of this phase.

The dedicated worker locks realm → policy → characters in ID order → progress →
new history/entitlement, with fences before mutation and commit. One transaction
stores all XP, immutable outcomes and the single entitlement. It never touches
inventory count. Only known rollbacks retry: 40001/40P01/55P03, and a 57014
statement timeout on the realm-fence lock, which a waiter queued behind two
holders can get instead of 55P03 (D-137). At most three retries with 50/100/200ms
backoff within a two-second worker budget. PostgreSQL 17's per-transaction
timeout enforces the remaining budget; its 25P04 terminates the session and is
not retried; socket uncertainty fails closed. See [PostgreSQL timeout semantics](https://www.postgresql.org/docs/17/runtime-config-client.html).
Ambiguous commits recover through the original immutable ID after restart, never
through an automatically allocated replacement. Stale-generation frozen work
cannot mutate. Recipient session changes are deliberately not a settlement fence.

Entitlements remain `available` at their saved location/deadline after restart.
Expired wall-clock deadlines do not consume the 64-unexpired-entitlement cap.
KO-09 performs no claim, expiry mutation, drop discovery or inventory UI; KO-10
will use the reserved tables/IDs and implement those operations. No available
row is itself permission to claim after its deadline. Backup restoration is the
rollback mechanism; old binaries reject schema 005 even before conversion.

## KO-10 extension

The same N3P1 bytes may now be cooked for engine10/wire5 with the existing requested-
life asset. That combination implements durable claims and expiry and permits
normal startup after explicit offline test-realm conversion. Engine9/wire4 retains
its settlement-only test gate; the historical KO-09 text above describes that
variant. [Loot format, authority, bounds and activation](loot.md).
